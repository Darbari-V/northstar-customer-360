Artefact 001 — Business Problem & Project Context

Start with a simple question: what is making customer enquiries difficult to manage, and what needs to be understood before choosing software?

Northstar Services is a fictional service business. Enquiries arrive through several channels, and different teams keep information in different places. Management reports follow-up and reporting concerns. This first document separates what the scenario tells us from explanations that still need evidence.

Where this fits: This is the starting point. It gives the later investigation, process analysis, requirements, data work and CRM design a reason to exist.

Evidence boundary: Northstar Services is fictional. The original document's scope, assumptions and limitations are retained below. Reader explanations are labelled “In plain English”; they do not represent new findings, approvals or implementation evidence.

Artefact
A work product, such as a requirements document, process map or data analysis.
Business analyst (BA)
A person who investigates a business situation, clarifies needs and helps define and evaluate changes.
CRM
Customer relationship management: the processes and systems used to organise customer relationships and related information.
Customer 360
The idea of bringing relevant customer information together into a more consistent view; it is the project's theme, rather than a completed product claim.
Enquiry / lead / prospect
An enquiry is an incoming request or expression of interest. A lead or prospect is a potential customer; the exact business definitions need agreement.
Stakeholder
Someone who affects the work, makes relevant decisions, or is affected by the proposed change.
Discovery / elicitation
Learning about the situation and drawing out needs through questions, observation, workshops or records.
Scenario fact / hypothesis
A scenario fact is supplied by the fictional brief. A hypothesis is a possible explanation still requiring evidence.
As-Is / To-Be
As-Is describes current working arrangements. To-Be describes a proposed future way of working.
Gap analysis
Comparing the current situation with the capability that would be needed, then identifying what must change.
Scope / baseline
Scope defines the boundaries of the work. A baseline is the selected reference version against which later changes are assessed.
Requirement
A statement of a capability, behaviour or quality needed to address a business or user need.
Business rule / functional requirement
A business rule sets a condition or restriction. A functional requirement describes system behaviour that supports the need or rule.
User story
A short explanation of who needs something, what they want and why it matters.
Acceptance criterion
A specific condition or example describing what an acceptable result would look like.
Traceability
Following a requirement back to its reason and forward to related design or verification work.
BO / GAP / SR / BR / FR / DR
Reference labels for business objective, gap, stakeholder requirement, business rule, functional requirement and data requirement.
BN / H / PP / NFR
Reference labels for business need, hypothesis, pain point and non-functional requirement. A non-functional requirement describes a quality the solution must meet, rather than a particular action.
REC / REV / REQ
REC-01 identifies a proposed reconciliation control; REV-01 identifies a proposed duplicate-review control. REQ references identify earlier learning exercises and do not add system features by themselves.
AS / AC / US / CR / OQ
Reference labels for assumption, acceptance criterion, user story, change request and open question.
DQ / VAL / D / T / Q
Reference labels for a data-quality finding, validation proposal, design decision, test scenario and SQL query.
Data model / entity / field
A data model describes information and relationships. An entity is a kind of record; a field is one piece of information stored about it.
Data dictionary
A reference explaining each field's meaning, form and applicable rules.
Schema / type / mandatory
A schema is the organised structure of a database. A type describes the kind of value stored. Mandatory means a value is required under an agreed rule.
Data completeness / accuracy / consistency
Completeness asks whether required values are present; accuracy asks whether values are correct; consistency asks whether related information agrees.
Normalisation / deduplication / identity resolution
Here, normalisation can mean bringing values into a comparable form. Deduplication reviews and resolves duplicate records; identity resolution determines which records refer to the same real customer. None is claimed as implemented.
Identifier / reference / foreign key
An identifier distinguishes a record. A reference points to another record. A foreign-key constraint can enforce valid references; the diagnostic fixture deliberately omits that constraint.
NULL / nullable
NULL means no value is stored in the illustrated database field. Nullable means the field can have no stored value.
Customer ID / assigned owner
Customer ID identifies the customer linked to an enquiry. The assigned owner identifies the Sales representative responsible for it; these are different relationships.
SQL / SQLite
SQL is a language for asking questions of structured data. SQLite is the database engine used for the synthetic exercise.
SELECT / FROM / WHERE
SELECT chooses what a query returns, FROM names its starting table, and WHERE applies conditions to individual rows.
LEFT JOIN / INNER JOIN
LEFT JOIN keeps every row from the starting table while looking for matches. INNER JOIN keeps only matching rows.
COUNT / GROUP BY / HAVING / ORDER BY
COUNT counts rows; GROUP BY groups matching values; HAVING filters groups; ORDER BY sorts results.
CREATE / INSERT / DROP
In the practice SQL file, CREATE defines a table, INSERT adds sample records, and DROP removes an existing practice table before recreating it. The fixture is a repeatable synthetic exercise, not a production setup.
IF / AND / THEN / ELSE
IF introduces a condition; AND requires both conditions to hold; THEN states the result if they hold; ELSE states what happens otherwise.
Synthetic data / fixture / staging
Synthetic data is invented for practice. A fixture sets up a repeatable example. Staging data is an intermediate set of records being checked before use.
Reconciliation / duplicate signal
Reconciliation compares sources record by record. A duplicate signal flags possible repetition for review, without proving that records should be merged or deleted.
KPI / baseline measure / ROI
A KPI is a key performance indicator. A baseline measure describes the starting position. ROI means return on investment; no achieved ROI is claimed here.
MVP / UAT
MVP means minimum viable product, a limited useful demonstration. UAT means user acceptance testing, checking the solution against agreed user needs.
Salesforce object / mapping
An object is a platform structure for a type of record. Mapping decides how a business concept or field corresponds to that structure.
Lead / Account / Contact / Opportunity
Salesforce record types for a potential buyer, an organisation or account, a person, and a qualified sales deal. Their suitability for Northstar is still being evaluated.
Picklist / Lookup / Auto Number
A picklist offers a defined set of values. A Lookup links a record to another record. Auto Number can generate a record reference automatically.
Validation / automation / pseudocode
Validation checks whether an action or value is allowed. Automation performs an action. Pseudocode expresses intended logic in readable steps without being a deployed program.
API / integration / migration
An API is an interface through which systems exchange requests or data. Integration connects systems; migration moves information between them.
SOP / handoff / escalation
An SOP is a standard operating procedure, a documented way to carry out work. A handoff transfers work or information to another person or team. An escalation raises an unresolved issue for further attention.
Permission / least privilege / audit
A permission controls who may view or change something. Least privilege gives people only the access needed for their work. An audit record helps trace relevant actions or changes.
Assumption / dependency / decision gate
An assumption is provisionally taken as true; a dependency is something the work relies on; a decision gate is a point where a choice must be resolved before moving forward.
B2B / B2C / session
B2B serves businesses; B2C serves individual consumers. Session in these documents refers to a learning stage, not a claimed client meeting.

1. Executive Summary

In plain English

This is the short version of the situation and the purpose of the analysis. A business analyst first understands the problem before recommending a tool.

Northstar Services is a fictional growing service organisation experiencing challenges in managing customer enquiries, prospect information and sales reporting across multiple business functions.

Customer enquiries are received through several channels, while information is maintained across spreadsheets, email accounts, individual notes and separate operational systems.

Management has reported inconsistent sales follow-ups, fragmented customer information and difficulty obtaining reliable sales and conversion reporting.

This case study investigates the business situation, identifies preliminary information-management and process-improvement needs, and establishes a foundation for subsequent requirements analysis and solution evaluation.

The initial Business Analysis approach is problem-led and technology-neutral. No specific CRM platform or technical solution has been selected at this stage.

2. Business Background

In plain English

This describes how the fictional business currently receives and handles information. Separate tools are a reason to investigate; their existence alone does not prove that a process is failing.

Northstar Services receives enquiries through several communication channels:

  • Website forms
  • WhatsApp
  • Telephone
  • Customer referrals
  • Marketing campaigns

The fictional scenario describes the following operating arrangements:

Business Area Current Arrangement
Website enquiries Received through a shared email inbox
WhatsApp enquiries Handled by two Sales representatives
Referral enquiries Sometimes received directly by individual Sales representatives

Sales operations Prospect information maintained in spreadsheets, emails and personal notes
Customer Support Separate ticketing application
Management reporting Weekly Excel-based sales reports

These arrangements indicate multiple information sources and workflows. However, the existence of separate tools alone does not establish that every process is inefficient or that a particular technology is required.

Further investigation would be needed to understand actual practices, information flows, operational constraints and opportunities for improvement.

3. Business Problem Statement

In plain English

A problem statement explains what the business cannot reliably do and why that matters. It does not assume that a particular software product is the answer.

Northstar Services does not currently have a clearly established, consistently evidenced approach for managing prospect and customer information across its different enquiry channels and business functions.

Management reports fragmented information, inconsistent follow-up activity and difficulties producing reliable sales reporting.

The differences in enquiry-handling methods and information storage may contribute to limited visibility of customer interactions, unclear ownership, incomplete records and inconsistent reporting inputs.

The precise causes, frequency and business impact of these issues remain unverified.

The business problem is therefore defined as a need to investigate and improve the consistency, visibility and reliability of customer information management and associated operational processes.

4. Symptoms, Possible Causes and Business Impact

In plain English

A symptom is something reported or noticed. A possible cause is an explanation to investigate. An impact is what that problem could mean for the business; these are kept separate.

It is important to distinguish observable or reported symptoms from possible underlying causes.

5. Preliminary Business Need

In plain English

A business need describes the capability the organisation needs, such as consistent information and clear responsibility. It can be stated before deciding how to build it.

Northstar Services needs more consistent and dependable processes and information-management capabilities to support the customer lifecycle.

Specifically, the organisation needs to establish how to:

  • Capture and maintain appropriate prospect and customer information consistently.
  • Identify responsibility for incoming enquiries and ongoing follow-up activities.
  • Track relevant customer interactions and lead progression.
  • Share customer information appropriately between authorised business functions.
  • Produce accurate, consistent and timely sales performance information.

The business need describes required capabilities and outcomes rather than prescribing a specific software product.

8. Preliminary Scope of Investigation

In plain English

Scope sets the boundary of this investigation. Read the in-scope and out-of-scope lists together to see what this stage covers and what it leaves for later.

In Scope

  • Enquiry sources and initial lead capture
  • Lead ownership, allocation and follow-up
  • Prospect and customer-information maintenance
  • Existing Sales and Support information-sharing practices
  • Current sales and conversion reporting processes
  • Data quality, consistency and potential duplication
  • Relevant technical, access-control and operational constraints
  • Identification and evaluation of potential improvement opportunities

Out of Scope at This Stage

  • Selecting or purchasing a CRM platform
  • Implementing Salesforce or another CRM
  • Executing a production data migration
  • Integrating live business applications
  • Making unsupported claims about revenue or conversion improvements
  • Performing an actual regulatory compliance audit

These boundaries apply to the initial business investigation and can be revisited following subsequent requirements analysis.

11. Assumptions, Dependencies and Open Questions

In plain English

Assumptions are things provisionally taken as true; dependencies are things the work relies on. Open questions identify what still needs to be found out. Also ask how many enquiries arrive through each channel; enquiry volumes help establish the scale of the investigation.

The following matters require clarification during subsequent analysis:

  • What constitutes a lead, opportunity, customer and support request?
  • Which information fields are collected by each enquiry channel?
  • What procedures currently govern assignment, reassignment and follow-up?
  • Which sales KPIs are important to management?
  • How are the weekly Excel reports prepared and reconciled?
  • What data-quality issues actually exist?
  • How is customer information shared between Sales and Customer Support?
  • What privacy, security, access and retention requirements apply?
  • Which existing systems could support improved processes?
  • What budgetary, operational or technological constraints affect solution choices?

Resolving these questions will help distinguish actual business requirements from untested assumptions.

12. Recommended Next Analysis Activities

In plain English

These are the proposed next steps for turning the initial problem description into better-supported analysis.

The next stages of the case study will focus on:

  1. Preparing and refining the stakeholder investigation plan.
  2. Establishing a preliminary As-Is process model from the scenario.
  3. Identifying pain points and testing root-cause hypotheses conceptually.
  4. Developing a proposed To-Be process for further analysis.
  5. Eliciting and documenting business, functional, non-functional and data requirements.
  6. Evaluating feasible CRM and customer-data solution options.

The project will progressively develop from analysis into practical technical demonstrations, with documentation and evidence added after the corresponding work is completed.

13. Project Integrity and Limitations

In plain English

This explains the evidence boundary. The work demonstrates analysis of a fictional scenario, without claiming client interviews, implementation or measured improvement.

This document is based on an independent, fictional business scenario.

Northstar Services is not presented as a real client, and this artefact does not claim that actual stakeholder interviews, workshops, observations or production-system assessments have occurred.

Reported challenges, analytical hypotheses, proposed improvements and completed deliverables are distinguished throughout.

The intention is to demonstrate a structured and defensible approach to Business Analysis while documenting practical learning and project development.
