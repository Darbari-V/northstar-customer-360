Artefact 006 — Proposed CRM Data & Solution Design (MVP V1)

This proposed-design stage asks how the existing exercise rules and data structures could be represented in a small CRM demonstration.

CRM means customer relationship management. Here, the design considers records, fields, relationships, views and validation rules that could support the earlier enquiry requirements. Salesforce is a candidate platform for the future demonstration. The document compares options and records open decisions; it does not claim that those options have been configured or tested.

Where this fits: Artefact 004 supplies the ownership and visibility requirements, and Artefact 005 supplies the exploratory customer-data work. This stage links them to a proposed minimum viable product: the smallest useful demonstration for the selected scope.

Evidence boundary: Northstar Services is fictional. The original document's scope, assumptions and limitations are retained below. Reader explanations are labelled “In plain English”; they do not represent new findings, approvals or implementation evidence.

Artefact
A work product, such as a requirements document, process map or data analysis.
Business analyst (BA)
A person who investigates a business situation, clarifies needs and helps define and evaluate changes.
CRM
Customer relationship management: the processes and systems used to organise customer relationships and related information.
Customer 360
The idea of bringing relevant customer information together into a more consistent view; it is the project's theme, rather than a completed product claim.
Enquiry / lead / prospect
An enquiry is an incoming request or expression of interest. A lead or prospect is a potential customer; the exact business definitions need agreement.
Stakeholder
Someone who affects the work, makes relevant decisions, or is affected by the proposed change.
Discovery / elicitation
Learning about the situation and drawing out needs through questions, observation, workshops or records.
Scenario fact / hypothesis
A scenario fact is supplied by the fictional brief. A hypothesis is a possible explanation still requiring evidence.
As-Is / To-Be
As-Is describes current working arrangements. To-Be describes a proposed future way of working.
Gap analysis
Comparing the current situation with the capability that would be needed, then identifying what must change.
Scope / baseline
Scope defines the boundaries of the work. A baseline is the selected reference version against which later changes are assessed.
Requirement
A statement of a capability, behaviour or quality needed to address a business or user need.
Business rule / functional requirement
A business rule sets a condition or restriction. A functional requirement describes system behaviour that supports the need or rule.
User story
A short explanation of who needs something, what they want and why it matters.
Acceptance criterion
A specific condition or example describing what an acceptable result would look like.
Traceability
Following a requirement back to its reason and forward to related design or verification work.
BO / GAP / SR / BR / FR / DR
Reference labels for business objective, gap, stakeholder requirement, business rule, functional requirement and data requirement.
BN / H / PP / NFR
Reference labels for business need, hypothesis, pain point and non-functional requirement. A non-functional requirement describes a quality the solution must meet, rather than a particular action.
REC / REV / REQ
REC-01 identifies a proposed reconciliation control; REV-01 identifies a proposed duplicate-review control. REQ references identify earlier learning exercises and do not add system features by themselves.
AS / AC / US / CR / OQ
Reference labels for assumption, acceptance criterion, user story, change request and open question.
DQ / VAL / D / T / Q
Reference labels for a data-quality finding, validation proposal, design decision, test scenario and SQL query.
Data model / entity / field
A data model describes information and relationships. An entity is a kind of record; a field is one piece of information stored about it.
Data dictionary
A reference explaining each field's meaning, form and applicable rules.
Schema / type / mandatory
A schema is the organised structure of a database. A type describes the kind of value stored. Mandatory means a value is required under an agreed rule.
Data completeness / accuracy / consistency
Completeness asks whether required values are present; accuracy asks whether values are correct; consistency asks whether related information agrees.
Normalisation / deduplication / identity resolution
Here, normalisation can mean bringing values into a comparable form. Deduplication reviews and resolves duplicate records; identity resolution determines which records refer to the same real customer. None is claimed as implemented.
Identifier / reference / foreign key
An identifier distinguishes a record. A reference points to another record. A foreign-key constraint can enforce valid references; the diagnostic fixture deliberately omits that constraint.
NULL / nullable
NULL means no value is stored in the illustrated database field. Nullable means the field can have no stored value.
Customer ID / assigned owner
Customer ID identifies the customer linked to an enquiry. The assigned owner identifies the Sales representative responsible for it; these are different relationships.
SQL / SQLite
SQL is a language for asking questions of structured data. SQLite is the database engine used for the synthetic exercise.
SELECT / FROM / WHERE
SELECT chooses what a query returns, FROM names its starting table, and WHERE applies conditions to individual rows.
LEFT JOIN / INNER JOIN
LEFT JOIN keeps every row from the starting table while looking for matches. INNER JOIN keeps only matching rows.
COUNT / GROUP BY / HAVING / ORDER BY
COUNT counts rows; GROUP BY groups matching values; HAVING filters groups; ORDER BY sorts results.
CREATE / INSERT / DROP
In the practice SQL file, CREATE defines a table, INSERT adds sample records, and DROP removes an existing practice table before recreating it. The fixture is a repeatable synthetic exercise, not a production setup.
IF / AND / THEN / ELSE
IF introduces a condition; AND requires both conditions to hold; THEN states the result if they hold; ELSE states what happens otherwise.
Synthetic data / fixture / staging
Synthetic data is invented for practice. A fixture sets up a repeatable example. Staging data is an intermediate set of records being checked before use.
Reconciliation / duplicate signal
Reconciliation compares sources record by record. A duplicate signal flags possible repetition for review, without proving that records should be merged or deleted.
KPI / baseline measure / ROI
A KPI is a key performance indicator. A baseline measure describes the starting position. ROI means return on investment; no achieved ROI is claimed here.
MVP / UAT
MVP means minimum viable product, a limited useful demonstration. UAT means user acceptance testing, checking the solution against agreed user needs.
Salesforce object / mapping
An object is a platform structure for a type of record. Mapping decides how a business concept or field corresponds to that structure.
Lead / Account / Contact / Opportunity
Salesforce record types for a potential buyer, an organisation or account, a person, and a qualified sales deal. Their suitability for Northstar is still being evaluated.
Picklist / Lookup / Auto Number
A picklist offers a defined set of values. A Lookup links a record to another record. Auto Number can generate a record reference automatically.
Validation / automation / pseudocode
Validation checks whether an action or value is allowed. Automation performs an action. Pseudocode expresses intended logic in readable steps without being a deployed program.
API / integration / migration
An API is an interface through which systems exchange requests or data. Integration connects systems; migration moves information between them.
SOP / handoff / escalation
An SOP is a standard operating procedure, a documented way to carry out work. A handoff transfers work or information to another person or team. An escalation raises an unresolved issue for further attention.
Permission / least privilege / audit
A permission controls who may view or change something. Least privilege gives people only the access needed for their work. An audit record helps trace relevant actions or changes.
Assumption / dependency / decision gate
An assumption is provisionally taken as true; a dependency is something the work relies on; a decision gate is a point where a choice must be resolved before moving forward.
B2B / B2C / session
B2B serves businesses; B2C serves individual consumers. Session in these documents refers to a learning stage, not a claimed client meeting.

1. Executive summary

In plain English

This is the proposed design in brief. MVP means minimum viable product: a limited demonstration focused on the selected enquiry behaviours, rather than a full enterprise CRM.

Northstar's simulated management concerns involve fragmented customer information, inconsistent enquiry follow-ups and reporting challenges. Artefacts 001–003 frame the problem and possible process gaps. Artefact 004 defines a bounded, author-selected fictional requirements baseline for Sales enquiry ownership and visibility. Artefact 005 investigates a limited Customer–Enquiry data model and data-quality exceptions using synthetic SQL records.

This document translates those existing requirements into a proposed CRM design for a limited MVP V1 demonstration. It identifies logical entities, candidate Salesforce object mappings, field choices, relationships, validations, manager views, design decisions still open and a test plan. The objective is not to create a full enterprise CRM architecture or rewrite prior requirements.

Recommended MVP boundary: capture and view synthetic Sales enquiries; optionally associate a customer record while identity is being confirmed (subject to decision D-01); maintain business-assigned Sales ownership; show the three scoped enquiry lists; and demonstrate BR-004's status-transition restriction. CRM configuration is the next workstream, not a completed output of Session 6.

3. Logical CRM model — deliberately platform-neutral

In plain English

An entity is a kind of thing the business records, such as a customer or enquiry. A Salesforce object is a platform representation of records. The mapping between those ideas is still a design decision.

CUSTOMER (illustrative logical entity)
  customer_id (logical unique key)
  name
  phone (mandatory? not decided)
       1
       | optional association for an unconfirmed enquiry [D-01 pending]
       | 0..many enquiries per customer
       v
SALES ENQUIRY (logical entity)
  enquiry_id (unique; DR-001)
  customer_id (possibly NULL under proposed MVP option; D-01)
  status (maintained; DR-002)
  assigned_owner_id (may be NULL; DR-003 / AS-02)
  description (candidate)
  next_follow_up_date (candidate)
       |
       | business assignment (not customer identification)
       v
SALES REPRESENTATIVE / USER (mapping to be selected)

A valid customer may be linked to many enquiries. An enquiry has at most one customer in the proposed logical model. The optional customer link is a new MVP candidate, not an approved replacement for Artefact 005's candidate VAL-01. The Sales representative relationship is logically separate. This sketch does not assert that a Customer custom object, Enquiry custom object, or any Salesforce relationship has been built.

BR-001 / FR-001 New Unassigned Enquiries: status exactly New AND business owner unset Both conditions required; manager-authorised view
BR-002 / FR-002 My Assigned Enquiries: for signed-in rep, all enquiries with matching business owner, including Closed Do not accidentally filter out Closed from this view
BR-003 / FR-003 Active Enquiry List: omit enquiries with status Closed Open is not the only eligible status
FR-004 Show owner's identity or the display text Unassigned when business owner missing Display label is not an actual rep or stored ID

DR-001 Maintain a unique enquiry identifier Map synthetic IDs separately from Salesforce record IDs

5.1 BR-004 — rule logic, not a configured formula

IF current_status = "New"
   AND requested_status = "Contacted"
   AND assigned_owner_id is unset
THEN reject the requested status transition
     with an actionable message:
     "Assign a Sales representative before changing this enquiry to Contacted."
ELSE BR-004 alone does not block the action.

No automatic status update: assigning REP-01 satisfies one prerequisite only. A separate authorised status-change action must still occur, and other defined rules (if any) may apply. This is pseudocode for business analysis, not a verified Salesforce validation formula. Exact platform logic and behaviour on record creation, imports and bulk operations will be tested after mapping.

6. Design decisions, conflicts and open questions

In plain English

Open decisions identify choices that must be resolved before build. D-01 considers temporarily missing customer identity; this is a new option and does not rewrite the earlier candidate Customer ID rule.

On a small screen, swipe across this table to read every column.

ID Question / tension Proposed disposition for MVP planning Status
D-01 Artefact 005 proposed VAL-01: valid Customer ID for new enquiries. Session 6 exercise wants enquiries temporarily without an identified customer. Evaluate allowing NULL customer link during an identity-pending stage. A non-null ID that points to no customer remains an unmatched-reference problem. If selected, record the deliberate exception and update the data rule and acceptance criteria in a new workstream; do not retroactively change VAL-01 or Artefact 004. Open
D-02 Which Salesforce object actually represents Sales Enquiry? Compare Lead and custom Enquiry object against current FR-001–FR-005 and future requirements; select one after environment review. Open
D-03 How is nullable business-assigned representative represented when Salesforce itself has a mandatory platform Owner? Keep a separate logical assignment from technical record ownership unless a defensible mapping is demonstrated. Open
D-04 Should status picklist contain all synthetic statuses or fewer? Confirm lifecycle, transition conditions and reporting meanings. Open
D-05 What happens to enquiries when customer links are removed, accounts merged, or customers deleted? Determine retention, privacy, lookup deletion behaviour and audit treatment before configuring. Open
D-06 Are next follow-up date and description required now? Treat as candidate fields; avoid quietly adding reminders or automation to FR-001–FR-005. Open
D-07 Who may assign owners and edit status? Clarify permissions and workflow separately from BR-004; do not infer a full security model from AS-06. Open

8. Practical MVP build order and evidence plan

In plain English

The build order explains how a future demonstration could proceed and what evidence would count as done. The definition of done has not yet been met.

  1. Decide object and ownership mappings (D-02/D-03); review free Salesforce environment and supported configuration.
  2. Create/configure a limited data structure (object(s), unique enquiry key, status values, business-owner reference, optional customer link if D-01 adopted).
  3. Load synthetic examples, clearly distinguishing allowed CRM records from deliberately invalid staging data used in Artefact 005.
  4. Implement three scoped views consistent with FR-001 to FR-004.
  5. Implement BR-004 precisely; verify it does not create automatic status changes.
  6. Run and record tests T-01–T-06 (and data-exception tests once D-01 is resolved); capture reproducible steps and actual pass/fail evidence.
  7. Publish demonstration evidence and a retrospective with explicit limits and any deviations from the proposed model.

Definition of done for the future MVP: a configured demonstration with synthetic records, reproducible evidence for the selected scope, documented actual test results, screenshots or equivalent proof, and published limitations. This definition of done is not yet met.
