Business analyst (BA)
A person who investigates a business situation, clarifies needs and helps define and evaluate changes.
CRM
Customer relationship management: the processes and systems used to organise customer relationships and related information.
Customer 360
The idea of bringing relevant customer information together into a more consistent view; it is the project's theme, rather than a completed product claim.
Enquiry / lead / prospect
An enquiry is an incoming request or expression of interest. A lead or prospect is a potential customer; the exact business definitions need agreement.
Stakeholder
Someone who affects the work, makes relevant decisions, or is affected by the proposed change.
Discovery / elicitation
Learning about the situation and drawing out needs through questions, observation, workshops or records.
Scenario fact / hypothesis
A scenario fact is supplied by the fictional brief. A hypothesis is a possible explanation still requiring evidence.
As-Is / To-Be
As-Is describes current working arrangements. To-Be describes a proposed future way of working.
Gap analysis
Comparing the current situation with the capability that would be needed, then identifying what must change.
Scope / baseline
Scope defines the boundaries of the work. A baseline is the selected reference version against which later changes are assessed.
Requirement
A statement of a capability, behaviour or quality needed to address a business or user need.
Business rule / functional requirement
A business rule sets a condition or restriction. A functional requirement describes system behaviour that supports the need or rule.
User story
A short explanation of who needs something, what they want and why it matters.
Acceptance criterion
A specific condition or example describing what an acceptable result would look like.
Traceability
Following a requirement back to its reason and forward to related design or verification work.
BO / GAP / SR / BR / FR / DR
Reference labels for business objective, gap, stakeholder requirement, business rule, functional requirement and data requirement.
BN / H / PP / NFR
Reference labels for business need, hypothesis, pain point and non-functional requirement. A non-functional requirement describes a quality the solution must meet, rather than a particular action.
REC / REV / REQ
REC-01 identifies a proposed reconciliation control; REV-01 identifies a proposed duplicate-review control. REQ references identify earlier learning exercises and do not add system features by themselves.
AS / AC / US / CR / OQ
Reference labels for assumption, acceptance criterion, user story, change request and open question.
DQ / VAL / D / T / Q
Reference labels for a data-quality finding, validation proposal, design decision, test scenario and SQL query.
Data model / entity / field
A data model describes information and relationships. An entity is a kind of record; a field is one piece of information stored about it.
Data dictionary
A reference explaining each field's meaning, form and applicable rules.
Schema / type / mandatory
A schema is the organised structure of a database. A type describes the kind of value stored. Mandatory means a value is required under an agreed rule.
Data completeness / accuracy / consistency
Completeness asks whether required values are present; accuracy asks whether values are correct; consistency asks whether related information agrees.
Normalisation / deduplication / identity resolution
Here, normalisation can mean bringing values into a comparable form. Deduplication reviews and resolves duplicate records; identity resolution determines which records refer to the same real customer. None is claimed as implemented.
Identifier / reference / foreign key
An identifier distinguishes a record. A reference points to another record. A foreign-key constraint can enforce valid references; the diagnostic fixture deliberately omits that constraint.
NULL / nullable
NULL means no value is stored in the illustrated database field. Nullable means the field can have no stored value.
Customer ID / assigned owner
Customer ID identifies the customer linked to an enquiry. The assigned owner identifies the Sales representative responsible for it; these are different relationships.
SQL / SQLite
SQL is a language for asking questions of structured data. SQLite is the database engine used for the synthetic exercise.
SELECT / FROM / WHERE
SELECT chooses what a query returns, FROM names its starting table, and WHERE applies conditions to individual rows.
LEFT JOIN / INNER JOIN
LEFT JOIN keeps every row from the starting table while looking for matches. INNER JOIN keeps only matching rows.
COUNT / GROUP BY / HAVING / ORDER BY
COUNT counts rows; GROUP BY groups matching values; HAVING filters groups; ORDER BY sorts results.
CREATE / INSERT / DROP
In the practice SQL file, CREATE defines a table, INSERT adds sample records, and DROP removes an existing practice table before recreating it. The fixture is a repeatable synthetic exercise, not a production setup.
IF / AND / THEN / ELSE
IF introduces a condition; AND requires both conditions to hold; THEN states the result if they hold; ELSE states what happens otherwise.
Synthetic data / fixture / staging
Synthetic data is invented for practice. A fixture sets up a repeatable example. Staging data is an intermediate set of records being checked before use.
Reconciliation / duplicate signal
Reconciliation compares sources record by record. A duplicate signal flags possible repetition for review, without proving that records should be merged or deleted.
KPI / baseline measure / ROI
A KPI is a key performance indicator. A baseline measure describes the starting position. ROI means return on investment; no achieved ROI is claimed here.
MVP / UAT
MVP means minimum viable product, a limited useful demonstration. UAT means user acceptance testing, checking the solution against agreed user needs.
Salesforce object / mapping
An object is a platform structure for a type of record. Mapping decides how a business concept or field corresponds to that structure.
Lead / Account / Contact / Opportunity
Salesforce record types for a potential buyer, an organisation or account, a person, and a qualified sales deal. Their suitability for Northstar is still being evaluated.
Picklist / Lookup / Auto Number
A picklist offers a defined set of values. A Lookup links a record to another record. Auto Number can generate a record reference automatically.
Validation / automation / pseudocode
Validation checks whether an action or value is allowed. Automation performs an action. Pseudocode expresses intended logic in readable steps without being a deployed program.
API / integration / migration
An API is an interface through which systems exchange requests or data. Integration connects systems; migration moves information between them.
SOP / handoff / escalation
An SOP is a standard operating procedure, a documented way to carry out work. A handoff transfers work or information to another person or team. An escalation raises an unresolved issue for further attention.
Permission / least privilege / audit
A permission controls who may view or change something. Least privilege gives people only the access needed for their work. An audit record helps trace relevant actions or changes.
Assumption / dependency / decision gate
An assumption is provisionally taken as true; a dependency is something the work relies on; a decision gate is a point where a choice must be resolved before moving forward.
B2B / B2C / session
B2B serves businesses; B2C serves individual consumers. Session in these documents refers to a learning stage, not a claimed client meeting.

Result Pass for one direct API submission in Salesforce Developer Edition on 28 November 2026.

What would Sales find after a failed submission?

In plain English

Identify the expected outcome for each submission.

In Artefact 011, Maya Shah’s request for an office-furniture quote became enquiry ENQ-0007. I used the same fictional customer for a second request, this time for office chairs. I expected Salesforce to reject a request with an unrecognised field name, leave no record of that submission and preserve the earlier enquiry.

How I identified the second submission

In plain English

Use the description to distinguish two requests from the same person.

Maya supplied her email. In Postman I deliberately sent it under Enquiry_Emai__c, missing the final “l” in Email. The configured field is Enquiry_Email__c. I added a unique piece of text to the description so I could recognise this particular submission among Maya’s enquiries.

{
  "Enquirer_Name__c": "Maya Shah",
  "Enquiry_Emai__c": "maya@example.com",
  "Enquiry_Description__c": "S12-REJECT-01 | I'd like a quote for office chairs.",
  "Enquiry_Status__c": "New"
}

What Salesforce returned

In plain English

Restore the connection before evaluating the field error.

The first attempt returned 401 Unauthorized with INVALID_AUTH_HEADER. A read-only limits request produced the same error. After renewing authorisation, I ran the limits check again and received 200 OK. This established that the connection worked before I repeated the create request.

Salesforce then returned 400 Bad Request with INVALID_FIELD. Its message identified the misspelled email field on the Sales Enquiry object. This was the expected rejection.

What Salesforce actually stored

In plain English

Read the saved values to check the business outcome.

I ran this read-only Salesforce query and checked the description of every returned enquiry.

SELECT Name, Enquirer_Name__c, Enquiry_Email__c,
       Enquiry_Description__c, Enquiry_Status__c
FROM Sales_Enquiry__c
ORDER BY Name

On a small screen, swipe across this table to read every column.

Check Observation
Did I receive the full result? The query returned 200 OK, seven records and done: true.
Did the office-chairs submission appear? Zero descriptions contained S12-REJECT-01.
What happened to the earlier enquiry? ENQ-0007 still showed Maya Shah, maya@example.com, “I'd like a quote for office furniture.” and New.

The error explained why the second submission failed. Checking the stored records established the outcome for Sales. This test covered one direct request from Postman. The message a customer would see on a live website and the handling of a retry are separate checks.
