Artefact 002 — Stakeholder Identification & Investigation Plan

Having described the problem, the next question is: who should we learn from, what should we ask, and what evidence would help?

Different teams see different parts of an enquiry's journey. Sales may know about follow-ups, Marketing about incoming leads, Support about customer history, and IT about systems and access. This document plans how those perspectives could be investigated and checked against records.

Where this fits: Artefact 001 supplied the initial concerns. This plan explains how a real investigation could test them before process models and requirements are treated as agreed.

Evidence boundary: Northstar Services is fictional. The original document's scope, assumptions and limitations are retained below. Reader explanations are labelled “In plain English”; they do not represent new findings, approvals or implementation evidence.

Artefact
A work product, such as a requirements document, process map or data analysis.
Business analyst (BA)
A person who investigates a business situation, clarifies needs and helps define and evaluate changes.
CRM
Customer relationship management: the processes and systems used to organise customer relationships and related information.
Customer 360
The idea of bringing relevant customer information together into a more consistent view; it is the project's theme, rather than a completed product claim.
Enquiry / lead / prospect
An enquiry is an incoming request or expression of interest. A lead or prospect is a potential customer; the exact business definitions need agreement.
Stakeholder
Someone who affects the work, makes relevant decisions, or is affected by the proposed change.
Discovery / elicitation
Learning about the situation and drawing out needs through questions, observation, workshops or records.
Scenario fact / hypothesis
A scenario fact is supplied by the fictional brief. A hypothesis is a possible explanation still requiring evidence.
As-Is / To-Be
As-Is describes current working arrangements. To-Be describes a proposed future way of working.
Gap analysis
Comparing the current situation with the capability that would be needed, then identifying what must change.
Scope / baseline
Scope defines the boundaries of the work. A baseline is the selected reference version against which later changes are assessed.
Requirement
A statement of a capability, behaviour or quality needed to address a business or user need.
Business rule / functional requirement
A business rule sets a condition or restriction. A functional requirement describes system behaviour that supports the need or rule.
User story
A short explanation of who needs something, what they want and why it matters.
Acceptance criterion
A specific condition or example describing what an acceptable result would look like.
Traceability
Following a requirement back to its reason and forward to related design or verification work.
BO / GAP / SR / BR / FR / DR
Reference labels for business objective, gap, stakeholder requirement, business rule, functional requirement and data requirement.
BN / H / PP / NFR
Reference labels for business need, hypothesis, pain point and non-functional requirement. A non-functional requirement describes a quality the solution must meet, rather than a particular action.
REC / REV / REQ
REC-01 identifies a proposed reconciliation control; REV-01 identifies a proposed duplicate-review control. REQ references identify earlier learning exercises and do not add system features by themselves.
AS / AC / US / CR / OQ
Reference labels for assumption, acceptance criterion, user story, change request and open question.
DQ / VAL / D / T / Q
Reference labels for a data-quality finding, validation proposal, design decision, test scenario and SQL query.
Data model / entity / field
A data model describes information and relationships. An entity is a kind of record; a field is one piece of information stored about it.
Data dictionary
A reference explaining each field's meaning, form and applicable rules.
Schema / type / mandatory
A schema is the organised structure of a database. A type describes the kind of value stored. Mandatory means a value is required under an agreed rule.
Data completeness / accuracy / consistency
Completeness asks whether required values are present; accuracy asks whether values are correct; consistency asks whether related information agrees.
Normalisation / deduplication / identity resolution
Here, normalisation can mean bringing values into a comparable form. Deduplication reviews and resolves duplicate records; identity resolution determines which records refer to the same real customer. None is claimed as implemented.
Identifier / reference / foreign key
An identifier distinguishes a record. A reference points to another record. A foreign-key constraint can enforce valid references; the diagnostic fixture deliberately omits that constraint.
NULL / nullable
NULL means no value is stored in the illustrated database field. Nullable means the field can have no stored value.
Customer ID / assigned owner
Customer ID identifies the customer linked to an enquiry. The assigned owner identifies the Sales representative responsible for it; these are different relationships.
SQL / SQLite
SQL is a language for asking questions of structured data. SQLite is the database engine used for the synthetic exercise.
SELECT / FROM / WHERE
SELECT chooses what a query returns, FROM names its starting table, and WHERE applies conditions to individual rows.
LEFT JOIN / INNER JOIN
LEFT JOIN keeps every row from the starting table while looking for matches. INNER JOIN keeps only matching rows.
COUNT / GROUP BY / HAVING / ORDER BY
COUNT counts rows; GROUP BY groups matching values; HAVING filters groups; ORDER BY sorts results.
CREATE / INSERT / DROP
In the practice SQL file, CREATE defines a table, INSERT adds sample records, and DROP removes an existing practice table before recreating it. The fixture is a repeatable synthetic exercise, not a production setup.
IF / AND / THEN / ELSE
IF introduces a condition; AND requires both conditions to hold; THEN states the result if they hold; ELSE states what happens otherwise.
Synthetic data / fixture / staging
Synthetic data is invented for practice. A fixture sets up a repeatable example. Staging data is an intermediate set of records being checked before use.
Reconciliation / duplicate signal
Reconciliation compares sources record by record. A duplicate signal flags possible repetition for review, without proving that records should be merged or deleted.
KPI / baseline measure / ROI
A KPI is a key performance indicator. A baseline measure describes the starting position. ROI means return on investment; no achieved ROI is claimed here.
MVP / UAT
MVP means minimum viable product, a limited useful demonstration. UAT means user acceptance testing, checking the solution against agreed user needs.
Salesforce object / mapping
An object is a platform structure for a type of record. Mapping decides how a business concept or field corresponds to that structure.
Lead / Account / Contact / Opportunity
Salesforce record types for a potential buyer, an organisation or account, a person, and a qualified sales deal. Their suitability for Northstar is still being evaluated.
Picklist / Lookup / Auto Number
A picklist offers a defined set of values. A Lookup links a record to another record. Auto Number can generate a record reference automatically.
Validation / automation / pseudocode
Validation checks whether an action or value is allowed. Automation performs an action. Pseudocode expresses intended logic in readable steps without being a deployed program.
API / integration / migration
An API is an interface through which systems exchange requests or data. Integration connects systems; migration moves information between them.
SOP / handoff / escalation
An SOP is a standard operating procedure, a documented way to carry out work. A handoff transfers work or information to another person or team. An escalation raises an unresolved issue for further attention.
Permission / least privilege / audit
A permission controls who may view or change something. Least privilege gives people only the access needed for their work. An audit record helps trace relevant actions or changes.
Assumption / dependency / decision gate
An assumption is provisionally taken as true; a dependency is something the work relies on; a decision gate is a point where a choice must be resolved before moving forward.
B2B / B2C / session
B2B serves businesses; B2C serves individual consumers. Session in these documents refers to a learning stage, not a claimed client meeting.

1. Executive Summary

In plain English

This summarises the proposed investigation. Planning interviews or workshops is different from conducting them; no real sessions are claimed here.

The Northstar Customer 360 case study examines reported challenges with fragmented customer information, inconsistent lead follow-ups and difficulties producing reliable sales and conversion reports.

Understanding these challenges requires investigation across Sales, Marketing, Customer Support, Management and IT rather than relying on assumptions or selecting a CRM platform prematurely.

This document identifies preliminary stakeholder groups, assesses their likely interests, recommends appropriate investigation techniques and defines how the resulting evidence would be analysed and validated.

This is a proposed plan developed from a fictional business scenario. No actual stakeholder interviews, workshops, observations or system assessments have been conducted.

2. Investigation Objectives

In plain English

These are the questions the investigation is intended to answer. They keep the work focused on enquiry handling, information quality, responsibility and reporting.

The proposed investigation aims to:

  • Understand how customer enquiries are received, recorded and managed across communication channels.
  • Identify the people responsible for lead ownership, follow-up and changes in responsibility.
  • Understand how customer and prospect information is stored, updated and shared.
  • Examine the relationship between Sales and Customer Support workflows.
  • Establish how weekly sales reports are prepared and which reporting issues require investigation.
  • Identify applicable business rules, technical constraints, data-quality considerations and information-access requirements.
  • Obtain sufficient evidence to refine the As-Is process, validate or reject hypotheses, and define future business requirements.

The investigation should remain business-problem-led and solution-neutral.

5. Investigation Techniques and Rationale

In plain English

A technique is a way to gather information. Interviews explore individual experience, observation shows work in practice, and document analysis examines existing records.

Different questions require different investigation methods. A combination of techniques should reduce dependence on a single account of the current process.

On a small screen, swipe across this table to read every column.

Technique Intended Use Why It Is Appropriate Limitation
Interviews Understand stakeholder goals, responsibilities, problems and constraints Allows detailed questioning and follow-up May reflect perception rather than actual practice
Observation Understand how employees handle enquiries and maintain information Can reveal informal workarounds and undocumented steps Observation may affect behaviour; permissions are required
Cross-functional Workshop Compare perspectives and agree process boundaries and terminology Exposes handoff issues and competing assumptions Group dynamics may influence responses
Document Analysis Examine available SOPs, spreadsheets, reports and process instructions Establishes how procedures and data are documented Documents may be outdated or incomplete
Data and Report Analysis Investigate completeness, consistency, duplicates and KPI reliability Provides measurable evidence where suitable records exist Requires appropriate access, definitions and sufficient data quality
Process Walkthroughs / Scenarios Follow representative enquiries from capture to outcome Tests whether the process model covers normal and exceptional paths Illustrative examples may not represent every situation
Prototypes (Later Stage) Clarify proposed information fields, screens and workflows Helps validate ambiguous requirements Premature prototypes may bias stakeholders toward a particular solution

Recommended approach: Begin with interviews and document review, then use observation, data checks and cross-functional validation to confirm or challenge initial findings.

A survey is not proposed as the primary discovery technique because the immediate problem requires detailed workflow understanding. It could be useful later if many employees need to provide comparable feedback.

7. Core Investigation Questions

In plain English

These are proposed questions to ask during discovery. They are questions, not invented interview answers or established findings.

Lead Capture and Ownership

  1. Which channels generate enquiries, and how does each channel deliver them?
  2. Which details are captured at the point of entry?
  3. How are enquiries assigned to employees?
  4. What happens when the expected owner is unavailable?
  5. How are duplicate or repeat enquiries recognised?

Lead Management and Follow-Up

  1. Which lead statuses are currently used?
  2. How are interactions, follow-ups and outcomes recorded?
  3. Are follow-up deadlines, reminders or escalation rules defined?
  4. What causes a lead to be marked converted, lost or closed?
  5. Which steps differ between employees or enquiry channels?

Customer Information and Cross-Functional Processes

  1. Where is customer information stored and maintained?
  2. Who is authorised to view or update customer records?
  3. What information, if any, passes between Sales and Customer Support?
  4. How are errors, missing details and conflicting records resolved?

Management Reporting and Technology

  1. How are weekly Excel sales reports assembled?
  2. Which data sources and definitions contribute to each KPI?
  3. How are reporting totals checked for accuracy?
  4. What existing technology, security, privacy, cost or operational constraints apply?

These questions are starting points. Follow-up questions would depend on the evidence obtained.

9. Proposed Investigation Sequence

In plain English

The stages put the investigation in a sensible order: agree the purpose, understand working practices, examine information and check the resulting findings.

Stage 1 — Confirm Purpose and Scope

  • Review the business problem and preliminary objectives.
  • Identify the sponsor and decision-makers.
  • Confirm investigation boundaries, constraints and required access.
  • Agree on the terminology used for leads, enquiries, customers and conversions.

Stage 2 — Understand Current Working Practices

  • Conduct role-specific interviews.
  • Review available documents and examples.
  • Walk through representative enquiry scenarios.
  • Observe relevant activities where permitted.

Stage 3 — Examine Data and Reporting

  • Identify relevant data sources and owners.
  • Review report generation and KPI calculations.
  • Investigate data completeness, consistency and possible duplication.
  • Document limitations in available evidence.

Stage 4 — Validate Findings

  • Prepare a preliminary As-Is process model.
  • Compare accounts across stakeholder groups and available records.
  • Review disagreements, gaps and exceptional process paths.
  • Hold a cross-functional validation session where feasible.

Stage 5 — Establish Requirements Inputs

  • Produce an updated problem and root-cause assessment.
  • Record confirmed business rules and constraints.
  • Identify priorities and unresolved decisions.
  • Establish inputs for future To-Be design and requirements specification.

This is a recommended sequence, not an execution log.

11. Findings Validation and Stakeholder Communication

In plain English

Validation means checking that the analysis reflects the evidence and stakeholders' understanding. Triangulation means checking an explanation using more than one source or method.

Proposed validation practices include:

  • Comparing stakeholder statements with available documents and operational data.
  • Checking for contradictions between departments.
  • Asking process participants to review relevant As-Is process steps.
  • Confirming process boundaries, ownership and exceptional scenarios.
  • Reviewing KPI definitions with the responsible business owners.
  • Recording open questions and decisions requiring sponsor input.
  • Maintaining versioned documentation as assumptions are resolved.

Findings should not be described as stakeholder-approved until an actual review and approval have occurred.

12. Expected Investigation Outputs

In plain English

Outputs are the things the proposed investigation should produce, such as clearer process information and requirements inputs. Listing an output does not mean it has already been produced through real discovery.

If the proposed investigation were executed, its expected outputs would include:

  1. Confirmed stakeholder register and engagement priorities.
  2. Evidence-supported As-Is process models.
  3. Validated pain points and root-cause analysis.
  4. Business rules, ownership definitions and reporting requirements.
  5. Agreed initial business objectives and potential success measures.
  6. Identified information-quality and technical constraints.
  7. A structured input set for the requirements catalogue and future-state design.

For the current fictional case study, these remain expected outputs of the proposed plan, not evidence of completed fieldwork.
