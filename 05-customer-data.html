Artefact 005 — Customer Data Model, SQL Investigation & Data Quality Analysis

The next question is whether the information can support the process: can we identify customers, connect enquiries to them and explain differences between records?

A data model describes how information is organised and connected. SQL is a language for asking questions of that information. This document uses invented Customers, Enquiries and website/Sales records to demonstrate checks. A missing value and an identifier that points to no matching record are different problems; finding either does not prove its cause.

Where this fits: The earlier requirements established enquiry identifiers, status and Sales ownership. This stage adds a proposed customer-data model and diagnostic checks, keeping customer identity separate from the Sales representative responsible for an enquiry.

1. Executive Summary

In plain English

This summarises the deliberately planted data exceptions and the main analytical conclusion: finding a difference in sample records is not the same as proving a real operational failure.

Earlier Northstar artefacts described fragmented customer information and concerns about enquiry capture, ownership and reporting. This artefact examines a limited customer–enquiry data structure and demonstrates how an IT Business Analyst can use SQL to identify missing values, invalid links and differences between sources, then propose controls without asserting an unverified root cause.

Worked synthetic findings: one customer with no phone value (C-102), one enquiry referring to a nonexistent customer (ENQ-203), one enquiry with no Customer ID (ENQ-204), and two website submission IDs absent from a matching-period Sales register (WEB-303, WEB-305). These are deliberately planted examples, not observed Northstar defects.

Key BA conclusion: A detected anomaly is evidence of a difference or exception within the example dataset, not proof of its cause. Proposed validation, investigation and reconciliation steps would require business confirmation before implementation.

3. Proposed Logical Data Model

In plain English

The model describes the proposed relationships, while the data dictionary explains each field. A customer identifier links an enquiry to a customer; the owner identifier refers to the responsible Sales representative.

CUSTOMERS                                  ENQUIRIES
---------                                  ---------
customer_id  (unique identifier)    1 ──<  customer_id (customer reference)
name                                       enquiry_id  (unique identifier)
phone                                      status
                                           assigned_owner_id (may be NULL)

One customer may have many enquiries; each valid linked enquiry points to one customer.

This is a proposed logical structure, not an implemented database schema. For valid, linked records, a single Customers row can be referenced by multiple Enquiries rows. Unmatched records are intentionally present in the synthetic diagnostic dataset to illustrate data-quality checks.

Design boundary: assigned_owner_id refers conceptually to a Sales Representative, not to the customer. No Sales Representative table or full permissions model is built here. Source-channel and timestamp fields remain future design considerations, not invented existing data.

5. SQL Investigation and Results

In plain English

Each SQL query asks one specific question of the sample data. SELECT chooses the output, FROM chooses the starting table, JOIN connects tables and WHERE filters rows. Open the line-by-line explanation beneath any query for a slower walkthrough.

The following queries use SQLite-compatible SQL. For reproducibility, a standalone synthetic fixture and query script creates the four diagnostic tables and reproduces the sample results. The fixture deliberately does not enforce a foreign key, because the purpose is to detect unmatched references in imported or staged example records; it must not be mistaken for a recommended production schema.

Q-01 — Find customers with no phone value

SELECT Customers.customer_id, Customers.name
FROM Customers
WHERE phone IS NULL;
Read this query line by line
  1. SELECT Customers.customer_id, Customers.name

    Return the customer identifier and customer name.

  2. FROM Customers

    Start with the Customers table.

  3. WHERE phone IS NULL;

    Keep records where no phone value is stored. NULL means the value is missing in this fixture.

Expected result: C-102 | Rahul (one synthetic record). This is a completeness exception only if phone numbers are required for the relevant business process; it is not evidence that the phone number is inaccurate.

Q-02 — Find all enquiries without a matching customer

SELECT Enquiries.enquiry_id
FROM Enquiries
LEFT JOIN Customers
  ON Enquiries.customer_id = Customers.customer_id
WHERE Customers.customer_id IS NULL;
Read this query line by line
  1. SELECT Enquiries.enquiry_id

    Return the enquiry identifier, so each result can be traced to a record.

  2. FROM Enquiries

    Start with the Enquiries table.

  3. LEFT JOIN Customers

    Keep every enquiry while looking for a matching customer record.

  4. ON Enquiries.customer_id = Customers.customer_id

    Look for a match by comparing the customer identifiers stored in the two tables.

  5. WHERE Customers.customer_id IS NULL;

    Keep rows where the join found no matching customer. This can happen for an absent identifier or a recorded but unmatched identifier.

Expected result: ENQ-203, ENQ-204. The first has an unmatched non-null ID; the second has no stored ID. With a LEFT JOIN starting from Enquiries, Customers.customer_id IS NULL marks the absence of a joined customer row.

Q-03 — Isolate recorded but unmatched Customer IDs

SELECT Enquiries.enquiry_id
FROM Enquiries
LEFT JOIN Customers
  ON Enquiries.customer_id = Customers.customer_id
WHERE Customers.customer_id IS NULL
  AND Enquiries.customer_id IS NOT NULL;
Read this query line by line
  1. SELECT Enquiries.enquiry_id

    Return the enquiry identifier, so each result can be traced to a record.

  2. FROM Enquiries

    Start with the Enquiries table.

  3. LEFT JOIN Customers

    Keep every enquiry while looking for a matching customer record.

  4. ON Enquiries.customer_id = Customers.customer_id

    Look for a match by comparing the customer identifiers stored in the two tables.

  5. WHERE Customers.customer_id IS NULL

    Keep rows where the join found no matching customer. This can happen for an absent identifier or a recorded but unmatched identifier.

  6. AND Enquiries.customer_id IS NOT NULL;

    Also require the enquiry to contain an identifier. This separates an unmatched recorded ID from an empty ID.

Expected result: ENQ-203 only. ENQ-204 is excluded because its enquiry-side Customer ID is NULL.

Q-04 — Find enquiries with a missing stored Customer ID

SELECT enquiry_id
FROM Enquiries
WHERE customer_id IS NULL;
Read this query line by line
  1. SELECT enquiry_id

    Return the enquiry identifier.

  2. FROM Enquiries

    Start with the Enquiries table.

  3. WHERE customer_id IS NULL;

    Keep enquiries that have no stored customer identifier.

Expected result: ENQ-204 only. This is a different problem from having an ID that does not match a customer.

Q-05 — Show matching customer–enquiry links

SELECT Enquiries.enquiry_id, Customers.name
FROM Enquiries
INNER JOIN Customers
  ON Enquiries.customer_id = Customers.customer_id
ORDER BY Enquiries.enquiry_id;
Read this query line by line
  1. SELECT Enquiries.enquiry_id, Customers.name

    Return each matching enquiry identifier together with the customer name.

  2. FROM Enquiries

    Start with the Enquiries table.

  3. INNER JOIN Customers

    Keep only enquiries that match a customer record. Unmatched enquiries are excluded.

  4. ON Enquiries.customer_id = Customers.customer_id

    Look for a match by comparing the customer identifiers stored in the two tables.

  5. ORDER BY Enquiries.enquiry_id;

    Sort the results by enquiry identifier.

Expected result: ENQ-201 | Asha and ENQ-202 | Rahul. INNER JOIN excludes unmatched records and therefore is not suitable by itself for investigating missing links.

Q-06 — Reconcile website submissions to the Sales register

SELECT WebsiteSubmissions.submission_id
FROM WebsiteSubmissions
LEFT JOIN SalesEnquiryRegister
  ON WebsiteSubmissions.submission_id = SalesEnquiryRegister.submission_id
WHERE SalesEnquiryRegister.submission_id IS NULL
ORDER BY WebsiteSubmissions.submission_id;
Read this query line by line
  1. SELECT WebsiteSubmissions.submission_id

    Return the identifier of each website submission found by the check.

  2. FROM WebsiteSubmissions

    Start with the website submissions for the illustrative reporting period.

  3. LEFT JOIN SalesEnquiryRegister

    Keep every website submission while looking for its corresponding entry in the Sales register.

  4. ON WebsiteSubmissions.submission_id = SalesEnquiryRegister.submission_id

    Match the two sources using the same submission identifier.

  5. WHERE SalesEnquiryRegister.submission_id IS NULL

    Keep website submissions for which the join found no Sales register entry.

  6. ORDER BY WebsiteSubmissions.submission_id;

    Sort the results by website submission identifier.

Expected result: WEB-303, WEB-305.

The count difference agrees with the two IDs in this particular fixture. Comparing counts alone is insufficient in general: equal totals may still hide different or duplicate IDs. Identifier-level reconciliation is therefore preferred.

Q-07 — Candidate duplicate signal (not a duplicate determination)

SELECT phone, COUNT(*) AS number_of_customers
FROM Customers
WHERE phone IS NOT NULL
GROUP BY phone
HAVING COUNT(*) > 1;
Read this query line by line
  1. SELECT phone, COUNT(*) AS number_of_customers

    Return each phone value and the number of customer records using it. The count column is named number_of_customers.

  2. FROM Customers

    Start with the Customers table.

  3. WHERE phone IS NOT NULL

    Leave out missing phone values before looking for repeated recorded values.

  4. GROUP BY phone

    Put customer records with the same phone value into a group.

  5. HAVING COUNT(*) > 1;

    Keep groups containing more than one record. A shared phone value is a review signal, not proof of a duplicate customer.

Expected result: no rows in the current synthetic fixture. Shared phone numbers can be legitimate, so matching phone values would only prompt review, not automatic deletion or merging. This check is illustrative and does not establish full duplicate-detection requirements.

9. Verification, Assumptions and Limits

In plain English

Verification describes how the synthetic exercise was checked and which assumptions limit the result. It does not turn sample records into production evidence.

Reproducibility: The included SQL fixture uses deliberately simplified SQLite-compatible tables, loads exactly the synthetic records shown above, and runs Q-01–Q-07. The queries and expected outputs were locally checked against that fixture during preparation. This demonstrates SQL reasoning on fabricated data only; it is not application UAT, database deployment, production reconciliation or real-world acceptance testing.

Key assumptions: ID matching is exact text equality; the two submission lists refer to the same period; NULL is an absent stored value; sample status labels are illustrative; there are no unstated customer matches. Production identity resolution could require normalisation, deduplication, source-system keys and exceptions, none of which are implemented here.

Quality limitations: The dataset is intentionally tiny and cannot support statistical claims, business KPIs, error-rate estimates, contactability conclusions, or decisions about retention/security policy. The root causes of its planted exceptions are unspecified on purpose.

Artefact 005 · Finalised case-study analysis · Customer Data & SQL

Customer Data Model & Data Quality Analysis

From enquiry records to a simple customer–enquiry model: documenting data, investigating broken references with SQL, reconciling submission lists and proposing sensible validation rules.

Session 5 analysis completedSynthetic SQLite evidenceNo production implementation
Evidence boundary: Northstar Services is fictional. All records, names, identifiers, findings and controls are invented for this independent case study. The SQL was checked against synthetic local fixtures only; this is not live client data, a deployed database, real stakeholder approval or CRM implementation.

Why this analysis matters

Northstar's earlier scenario raised concerns about fragmented customer information and inconsistent enquiry handling. This artefact responds to BO-01 (consistent enquiry/customer-data capture) and GAP-01 (customer-information consistency), while respecting the enquiry ownership baseline defined in Artefact 004.

Problem to investigate

Missing or inconsistent information

A customer may lack a relevant contact field, or an enquiry may refer to a customer that cannot be found.

Approach

Define → query → compare → investigate

Describe the data, run checks, document synthetic exceptions and propose controls without guessing the root cause.

Proposed logical data model

Entity 1

Customers

customer_id — unique customer identifier

name — customer name

phone — contact telephone number

Entity 2

Enquiries

enquiry_id — unique enquiry identifier

customer_id — link to customer

status — enquiry stage

assigned_owner_id — Sales owner, nullable

1 customer → many enquiries · linked by customer_id

Critical distinction: an enquiry can reference a valid customer and still be unassigned to a Sales Representative. Artefact 004 explicitly allows a missing assigned_owner_id in some cases; this document does not relabel those cases as data-quality failures.
