Customer Data Model & Data Quality Analysis

From enquiry records to a simple customer–enquiry model: documenting data, investigating broken references with SQL, reconciling submission lists and proposing sensible validation rules.

Session 5 analysis preparedSynthetic SQLite evidenceNo production implementation
Evidence boundary: Northstar Services is fictional. All records, names, identifiers, findings and controls are invented for this independent case study. The SQL was checked against synthetic local fixtures only; this is not live client data, a deployed database, real stakeholder approval or CRM implementation.

Why this analysis matters

Northstar's earlier scenario raised concerns about fragmented customer information and inconsistent enquiry handling. This artefact responds to BO-01 (consistent enquiry/customer-data capture) and GAP-01 (customer-information consistency), while respecting the enquiry ownership baseline defined in Artefact 004.

Problem to investigate

Missing or inconsistent information

A customer may lack a relevant contact field, or an enquiry may refer to a customer that cannot be found.

Approach

Define → query → compare → investigate

Describe the data, run checks, document synthetic exceptions and propose controls without guessing the root cause.

Proposed logical data model

Entity 1

Customers

customer_id — unique customer identifier

name — customer name

phone — contact telephone number

Entity 2

Enquiries

enquiry_id — unique enquiry identifier

customer_id — link to customer

status — enquiry stage

assigned_owner_id — Sales owner, nullable

1 customer → many enquiries · linked by customer_id

Critical distinction: an enquiry can reference a valid customer and still be unassigned to a Sales Representative. Artefact 004 explicitly allows a missing assigned_owner_id in some cases; this document does not relabel those cases as data-quality failures.

SQL: identify the differences

Q-01 · Missing phone values

SELECT Customers.customer_id, Customers.name
FROM Customers
WHERE phone IS NULL;

Expected: C-102 | Rahul

Q-02 · Enquiries without a matching customer

SELECT Enquiries.enquiry_id
FROM Enquiries
LEFT JOIN Customers
  ON Enquiries.customer_id = Customers.customer_id
WHERE Customers.customer_id IS NULL;

Expected: ENQ-203, ENQ-204

Q-03 · Recorded Customer ID, but no customer match

SELECT Enquiries.enquiry_id
FROM Enquiries
LEFT JOIN Customers
  ON Enquiries.customer_id = Customers.customer_id
WHERE Customers.customer_id IS NULL
  AND Enquiries.customer_id IS NOT NULL;

Expected: ENQ-203 only

The second condition excludes ENQ-204, because that enquiry has no Customer ID stored at all. The full document includes separate missing-reference, matching-record and duplicate-signal queries.

Accuracy, timeliness, privacy compliance and confirmed customer duplication cannot be assessed from these records. A phone-number match is at most a duplicate-review signal, not grounds for automatic merging.

Candidate validation and review controls

IDProposed approachQuestion before approval
VAL-01New enquiries reference an existing Customer IDHow do first-time customers get registered before their enquiry is accepted?
VAL-02Check required contact fields for the chosen channelIs phone required, or can another contact method be valid?
VAL-03Ensure unique Enquiry IDsHow are source-system IDs generated or reconciled?
REC-01Compare submission IDs for an agreed periodWho owns exception reviews and how are delays handled?
REV-01Review possible duplicates before mergingWhich matching criteria and approvals are appropriate?
Important workflow exception: A strict rule requiring an already-existing customer can inadvertently block a new customer's first enquiry. A customer-creation or provisional-capture process must be designed before VAL-01 can be approved. These rules are proposals, not additions to an approved production baseline.
